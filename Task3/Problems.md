# Проблемы и риски текущей архитектуры

| # | Проблема | Комментарий |
|---|---|---|
| P1 | Клиентский запрос проходит через всю синхронную цепочку до внешних страховых компаний | Ответ уходит только после возврата последнего ответчика, то есть задержка определяется самой медленной компанией, а ее ошибка валит весь запрос |
| P2 | Интеграции и сервисы не разделены границами отказа | Один зависший вызов занимает поток и соединение, сбой перейдет на соседей: данные у остальных уже есть, а ответ не уходит |
| P3 | Данные подтягиваются по календарю, а не по факту изменений | Тарифы меняются редко, поэтому большинство опросов впустую создают трафик и конкурируют с пользовательскими запросами за ресурсы |
| P4 | Частоту опроса невозможно подобрать удачно | Реже - клиент видит несуществующие тарифы, чаще - перегружаем API страховых компаний; сам конфликт интервалом не решается |
| P5 | Локальные копии продуктов отстают от источника | До 15 минут в core-app и до суток в ins-comp-settlement - в этом окне пользователю показывается устаревшая цена |
| P6 | Опрос отдает только снимок текущего момента, история изменений не сохраняется | Если между двумя опросами тариф поменялся дважды, промежуточное значение не зафиксируют, хотя страховка могла быть оформлена именно по нему |
| P7 | Пакетные объемы и жесткая связанность по времени растут вместе с бизнесом | Ночная выгрузка едет одним блоком (падение таймаутов после рекламной кампании), реестр ждет доступности core-app сутки, а рост числа страховых и ретраи при ошибках дают большое количество внешних вызовов |

# Миграция на Event-Streaming

Топологию сервисов менять не планируем: в страховые по-прежнему обращается только ins-product-aggregator. Меняется способ доставки его результатов до потребителей.

В схему добавляется брокер событий Kafka с двумя топиками:

| Топик | Источник | Потребители | Содержимое |
|---|---|---|---|
| insurance.products | ins-product-aggregator | core-app, ins-comp-settlement | Текущие продукты и тарифы |
| insurance.policies | core-app | ins-comp-settlement | События о созданных полисах |

## Какие проблемы это закрывает

| Решение | Закрываемые проблемы |
|---|---|
| Агрегатор сам опрашивает страховые и один раз публикует результат в общий канал — потребителям не нужно опрашивать его по индивидуальному расписанию | P1, P3 |
| Читатели работают с топиком и не связаны доступностью агрегатора или друг друга; после перебоя возобновляют чтение с места остановки | P2 |
| Сообщения приходят в момент изменения данных, а не через фиксированные интервалы | P4 |
| Ночная пачка заменяется непрерывным потоком, ins-comp-settlement обрабатывает его постепенно в течение дня | P5, P7 |
| Каждая правка тарифа становится отдельным сообщением в топике, история сохраняется | P6 |

Компактирование топика insurance.products выполняется для того, чтобы свежий потребитель мог восстановить полное текущее состояние исключительно из топика.

Частично проблема P2 решается не полностью: брокер устраняет взаимозависимость внутренних сервисов, но агрегатор продолжает ходить во внешние API страховых. Поэтому на каждую внешнюю интеграцию выделяется отдельный пул соединений и отдельный пул потоков (паттерн Bulkhead) — сбой одной компании не задевает остальные.

# Transactional Outbox

Применяется в core-app.

При создании полиса core-app должен одновременно сохранить его в базе и опубликовать событие в Kafka. Если только записать в базу, но опубликовать не выйдет — ins-comp-settlement о новом полисе не узнает и тот не попадет в реестр. Если опубликовать, но не записать в базу — в реестре окажется полис, которого нет в системе.

Чтобы избежать расхождений, событие помещается в outbox-таблицу в рамках той же транзакции, что и сам полис. Отдельный процесс периодически читает эту таблицу и передает события в брокер.

В ins-product-aggregator outbox избыточен: он не хранит состояние и ничего не пишет в базу, а лишь публикует полученные от страховых данные. Двойной записи нет, соответственно, нет и риска потери.
